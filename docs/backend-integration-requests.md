# Что требуется от backend-команды для интеграции семи UI-сценариев

Проверено по коду репозитория 24.10.2026: `backend/app/api/v1`, Pydantic-схемам
и сервисам. Ниже различаются реализованные обработчики, явные `501` и отсутствующие
контракты. Это проверка кода, не отчёт о пройденных сквозных API-тестах.
Backend в этой задаче не изменялся; его доработки выполняет backend-команда.
Все пути ниже имеют префикс `/api/v1`.

## Уже есть — можно подключать без новых endpoint

| UI | Действующие обработчики |
|---|---|
| Вход клиента / сотрудника | `POST /auth/login/phone`, `POST /auth/login`, `GET /me` |
| Каталог, реквизиты по ИНН | `GET /products`, `GET /products/{id}`, `GET /companies/lookup?inn=…` |
| Черновик и параметры | `POST /applications`, `GET /applications`, `GET/PATCH /applications/{id}` |
| Согласия, предварительный лимит, подача | `POST/GET /applications/{id}/consents`, `GET /applications/{id}/pre-approval`, `POST /applications/{id}/submit` |
| Автоматический статус | `GET /applications/{id}`: `client_status`, `status_description`, `available_actions`, `version`; таймерные demo-переходы заменить polling реального состояния |
| История | `GET /applications/{id}/history` |
| Оффер и отказ клиента | `GET /applications/{id}/offer`, `POST /applications/{id}/offer/accept`, `POST /applications/{id}/offer/reject` |
| Подпись, договор, график, кредиты | `POST /applications/{id}/sign`, `GET /applications/{id}/contract`, `GET /loans`, `GET /loans/{id}` |
| Сотрудники / администратор | `GET /backoffice/applications`, `GET /backoffice/applications/{id}`; admin уже видит все заявки |
| Назначение, заключение, решения | `POST /backoffice/applications/{id}/assign`, `/analyst-conclusion`, `/decision` |

Андеррайтер уже может запросить документы или экспертизу через `/decision`:
`decision_type=more_information_required` и `more_info_target=client/credit_analyst`.
Не нужен второй endpoint для тех же действий. При запросе клиенту передаётся
`info_request`, аналитику — `comment`. Одобрение и контр-предложение требуют суммы,
срока и ставки; отказ — непустого `reasons`.

## P0: блокирует полноценный показ сценариев

### 1. Чат клиента — контракта нет

Нужны сохранённая история диалога, отправка сообщения и привязка к клиенту,
компании и заявке. В UI используются сообщения, предложение параметров,
подтверждение/редактирование заявки, статусы, дозапросы и объяснение отказа.

Согласовать точные URL и JSON. Предложение для обсуждения, не существующий API:
`GET/POST /applications/{id}/messages`. Для диалога до появления черновика нужен
отдельный conversation ID либо документированное создание черновика заранее.
Минимум в сообщении: ID, роль автора, текст, дата, связь с заявкой/дозапросом;
для карточки параметров — структурированные сумма, срок, цель, продукт и залог.
Нужен способ не дублировать сообщение при повторе запроса.

Бизнес-команды и кредитное решение должны оставаться в backend. Нужен рабочий
fallback без модели. Внешняя модель с открытыми весами допустима с заменяемыми
base URL, ключом и названием модели; ключ не отправляется в браузер.

### 2. Документы клиента — четыре метода возвращают 501

| Метод | Уже объявленный контракт |
|---|---|
| `POST /applications/{id}/documents` | multipart: `file`, `type`, необязательный `info_request_id`; ответ `DocumentRead` |
| `GET /applications/{id}/documents` | `DocumentRead[]` |
| `GET /applications/{id}/documents/{document_id}/content` | Бинарное содержимое |
| `DELETE /applications/{id}/documents/{document_id}` | 204 |

Реализовать хранение файлов, проверку доступа и допустимости операции по статусу.
`DocumentRead` уже содержит ID, имя, MIME, размер, тип, дату и связь с дозапросом.
Согласовать разрешённые форматы и размер; для скачивания возвращать корректные
Content-Type и Content-Disposition. В UI нужны PDF и XLSX, а также договоры.

### 3. Ответы на дозапросы — два метода возвращают 501

- `GET /applications/{id}/info-requests` → `InfoRequestRead[]`.
- `POST /applications/{id}/info-requests/{rid}/answer` → `InfoRequestRead`;
  тело `{ "message": "…" }`, файлы загружаются заранее с `info_request_id`.

Реализовать частичное поступление комплекта, понятный список оставшихся документов
и корректное продолжение процесса после полного ответа. Нужны данные о периоде/
годе, когда они требуются в UI; текущий контракт содержит типы и общий текст.
Сценарий 2 нельзя полноценно пройти, пока загрузки и ответы остаются 501.

### 4. Запрос документов от аналитика — маршрута нет

В `schemas/document.py` есть `InfoRequestCreate`, но в роутере бэкофиса нет команды
создания дозапроса аналитиком. Требуется согласовать endpoint, допустимые этапы,
права исполнителя и возврат к аналитику после ответа клиента. Пример пути только
для обсуждения: `POST /backoffice/applications/{id}/info-requests`.
В макете аналитик передаёт текст и типы документов через ИИ; без модели запрос
всё равно должен сохраниться и появиться у клиента.

### 5. Файлы для сотрудников — нет маршрута скачивания с их ролью

Существующий `/applications/{id}/documents/{document_id}/content` объявлен для
`CurrentClient`; сотрудник не сможет использовать его напрямую даже после снятия
501. Нужен документированный способ скачать файл по доступной сотруднику заявке
с проверкой назначения/роли; admin — только в пределах разрешённого просмотра.
Метаданные документов уже включены в `BackofficeApplicationDetail`.

### 6. Полный профиль компании — три метода возвращают 501

`POST /companies`, `GET /companies`, `GET /companies/{id}`. Для отображения уже
привязанной компании в MVP особенно важен `GET /companies/{id}`; `/me` даёт только
ID, название и роль участия. Привязка новой компании не обязательна, если её нет
в согласованном MVP.

Для профиля из HTML дополнительно согласовать источник руководителя, должности,
права подписи, системы налогообложения, телефона, почты и расчётного счёта:
в `CompanyRead` этих полей нет. Не подставлять выдуманные значения вместо них.

## P1: действия и поля, которые также требуют решения команды

- **Документы на скачивание.** Договор и график уже доступны как JSON, но отдельных
  экспортов PDF/XLSX нет. Согласовать: серверный файл или печатная форма/экспорт
  на frontend по реальным данным. Для согласий API возвращает тип, подписанта и
  дату, но не файл; нужны тексты/шаблоны, если «Скачать» должно работать.
- **Принять экспертизу, вернуть с комментарием, напомнить, отозвать запрос.**
  В исходных UI есть эти действия, отдельных команд в API нет. `/assign`
  переназначает исполнителя и не заменяет принятие/отзыв экспертизы. Согласовать,
  какие действия входят в MVP и их изменения статуса/историю.
- **Очереди и счётчики вкладок.** Списки поддерживают `status`, `risk_zone`,
  `limit`, `offset`; scope уже ограничен ролью. Не хватает явных фильтров
  «новая эскалация / запрос андеррайтера / принятая экспертиза» и отделения текущих
  назначений от истории участия. Согласовать фильтры либо поля для вычисления
  вкладок. `assignee_id` есть, ФИО исполнителя в списке нет. Нужен способ показать
  реальное ФИО без недокументированного справочника пользователей.
- **Объяснение отказа клиенту.** `OfferRead.reasons` и `status_description` есть;
  доступность `/offer` для автоотказа подтвердить. Нужны безопасные клиентские
  причины и условия повторного обращения, если они выводятся в UI. Нельзя
  показывать клиенту внутренние скоринговые данные из банковской карточки.
- **Уведомления:** `GET /notifications` и `POST /notifications/{id}/read` — 501.
  Можно отложить при отсутствии отдельного UI уведомлений в MVP.
- **Подбор продукта:** `POST /products/match` — 501. Для MVP возможен явный выбор
  из рабочего `GET /products`; если подбор обещает чат, нужен контракт подбора.

## Что вернуть frontend-команде

1. Обновлённые OpenAPI, Postman и список реализованных методов с примерами ошибок.
2. Рабочие синтетические данные четырёх клиентских сценариев, роли и тестовые
   учётки, позволяющие провести одну заявку через клиента → сотрудника → клиента.
3. Конкретные ID или воспроизводимый seed; состояние должно сохраняться после
   обновления страницы. Ссылки на фиксированные HTML-фреймы не заменяют API.
4. Подтверждение auth/ролей и 401/403/404/409/422; версия заявки для PATCH.
5. Проверка сквозной цепочки документов/дозапроса и заключения/решения сотрудников.

Отдельный WebSocket/SSE не обязателен для MVP: frontend может опрашивать готовые
GET-методы. Сам переход статуса выполняется только серверной командой/конвейером.

Согласования по макету: SMS-вход в HTML расходится с действующим входом по телефону;
для согласий backend требует `bki`, `fns`, `digital_profile`, а UI показывает только
два документа. В сценарии 4 контр-предложение 2,5 млн / 18 мес., но часть графиков
в исходнике 3 млн / 24 мес.; после интеграции договор должен использовать принятые
условия из API. Эти расхождения нужно согласовать, не скрывать под статическим UI.
